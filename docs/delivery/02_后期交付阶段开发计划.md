# 后期交付完善范围与依赖清单

> **项目：** 基于智慧家居场景的大语言模型智能体科研应用一体机  
> **更新日期：** 2026-04-27  
> **文档定位：** 当前阶段用于确认后期交付范围、依赖和证据链，不直接作为开发排期  
> **核心路线：** 前端/后端统一后台 + Dify 智能体编排 + Home Assistant 统一设备抽象 + Ollama 本地模型

---

## 一、交付推进原则

1. **先定范围，再开发**：当前重点不是立即写功能，而是明确哪些模块已经有基础、哪些需要完善、哪些必须等硬件确认。
2. **Dify 作为智能体入口**：平台对话走 Dify；Dify 通过后端标准接口调用设备、数据、知识库和系统能力。
3. **HA 作为设备统一抽象**：平台不直接绑定小米云，优先让小米设备进入 HA，再由平台通过 HA 实体进行状态查询和控制。
4. **真实沙盘单独管理**：当前虚拟沙盘只能作为临时兜底；线下真实电子沙盘需要等协议确认后重写适配。
5. **验收证据优先**：每个合同条款都要能落到页面入口、操作步骤、接口证据、日志或截图。
6. **页面存在不等于模块完成**：每个页面必须按业务闭环、交互组件、后端接口、异常状态、日志审计和验收证据评审，不能只用卡片、列表、新增按钮包装成完成。

## 三、专项一：安全与运行时配置

### 当前问题

- 仓库配置中出现真实数据库连接、HA Token、Dify App Key、Dataset Key、Agent Key。
- Dify DSL 中存在公网地址和明文 App Key。
- 沙盘接口存在向浏览器返回 HA Token 的风险。

### 完善目标

- `config.yaml` 只保留本地兜底和占位值。
- 真实配置通过环境变量、系统设置或交付部署文件注入。
- 已暴露密钥必须轮换，并记录轮换日期、负责人、验证方式。
- Dify DSL 模板中只保留占位变量和配置说明。

### 验收证据

| 证据 | 说明 |
|---|---|
| 配置文件截图 | 仓库内无真实 Token/密码 |
| 系统设置截图 | Dify、HA、Ollama 运行时配置可查看/测试 |
| 密钥轮换记录 | 已泄露凭证已作废 |
| 服务连接测试 | 新配置可连接 Dify、HA、Ollama |

## 四、专项二：Dify 智能体真实链路

### 当前问题

- 主 Chatflow 和子 Workflow 模板已去公网地址和明文 Key，交付环境仍需替换占位并实测。
- 数据查询 Workflow 已改为调用后端 `/monitor/agent-query`，但目标环境需验证 HA 实时/历史数据。
- RAG Workflow `dataset_ids` 仍为空，交付环境需要绑定真实知识库。
- Agent 实例已有 CRUD，但平台内调用/测试能力不足。

### 完善目标

| 能力 | 目标链路 | 验收方式 |
|---|---|---|
| 设备控制 | Dify -> `/api/v1/devices/search` -> `/api/v1/devices/{entity_id}/control` -> HA | 对话开关灯，设备页状态变化 |
| 数据查询 | Dify -> `/api/v1/monitor/agent-query` -> 后端监控/HA History | 对话查询温湿度/趋势，返回真实数据来源 |
| 知识库检索 | Dify RAG -> 绑定 dataset -> 返回文档片段 | 提问系统文档问题，返回来源内容 |
| 系统接口 | Dify -> 后端健康/监控接口 | 查询系统状态，返回服务健康 |
| 实例调用 | 平台 Agent 实例 -> Dify App/Workflow API | 在 `/agents` 触发测试并记录结果 |

### 交付注意

- Dify 节点响应中需保留 `workflow_run_id` 或运行详情，便于专家查看“智能体确实执行了流程”。
- 所有后端 Agent 调用使用 `X-Agent-Key`，但 Key 不能写死到仓库模板。
- 数据不足时允许 fallback，但必须在响应或文档中标注，不能伪装成真实历史。

## 五、专项三：Home Assistant 与小米设备接入

### 接入策略

平台只对接 HA，不直接对接小米云。HA 内部可按设备条件采用：

1. Matter/Thread/Wi-Fi 本地接入。
2. 小米官方 `ha_xiaomi_home` 集成。
3. HA 官方 `xiaomi_miio` 支持范围内的设备。
4. Zigbee/MQTT/网关方案。
5. 第三方 `hass-xiaomi-miot` 作为兼容兜底。

### 设备兼容矩阵模板

| 设备名称 | 型号 | 协议/接入方式 | HA entity | 可查询状态 | 可控制动作 | 是否本地可用 | 是否依赖外网 | 验收用途 | 备注 |
|---|---|---|---|---|---|---|---|---|---|
| 客厅灯 | 待确认 | Matter/小米/网关 | 待确认 | on/off/亮度 | turn_on/turn_off/set_brightness | 待确认 | 待确认 | 设备控制 | 待硬件清单 |
| 温湿度传感器 | 待确认 | Matter/小米/网关 | 待确认 | 温度/湿度 | 只读 | 待确认 | 待确认 | 传感器数据 | 待硬件清单 |
| 场景/模式 | 待确认 | HA scene/script | 待确认 | 场景状态 | activate | 待确认 | 待确认 | 场景信息 | 待配置 |

### 验收策略

- 只能依赖小米云的设备可作为扩展演示，但不作为“断网可用”核心证据。
- 最终验收文档需标注每个设备是否依赖外网。

## 六、专项四：真实电子沙盘

### 当前定性

- 当前 `/sandbox` 和后端沙盘接口可作为 **HA 虚拟设备沙盘** 的临时联调和兜底演示。
- 它不能替代线下真实电子沙盘。
- 正式交付实现应等待真实沙盘硬件资料确认后重写适配层。

### 硬件方需提供资料

| 类别 | 需要确认的问题 |
|---|---|
| 通信方式 | HTTP、MQTT、WebSocket、TCP、串口、Modbus 或厂家 SDK |
| 网络拓扑 | 沙盘是否与一体机同局域网，是否需要固定 IP、网关或中间控制器 |
| 设备点位 | 房间、灯光、窗帘、门锁、传感器、屏幕、执行器等点位清单 |
| 状态数据 | 每个点位返回字段、单位、刷新频率、在线/离线状态 |
| 控制命令 | 开关、亮度、模式、场景、复位、急停等命令格式 |
| 场景接口 | 是否支持场景列表、场景执行、场景状态回读 |
| 安全鉴权 | API Key、账号密码、证书、白名单或无鉴权 |
| 异常处理 | 超时、设备离线、命令失败、状态不一致时的返回格式 |
| 联调工具 | 是否提供 Postman、SDK、模拟器、协议文档或测试账号 |

### 后续适配方向

- 后端新增真实沙盘适配层，隔离不同硬件协议。
- 前端沙盘页面根据真实点位重新设计，不直接复用当前虚拟设备布局。
- 当前虚拟沙盘保留为“无硬件演示/开发联调/故障兜底”。

## 七、专项五：页面与模块完整性

### 当前问题

- 部分页面已经有菜单、卡片、列表或新增按钮，但缺少完整业务闭环。
- 如果后续 AI 只围绕单次需求补一个局部功能，容易出现“页面看起来满足合同参数，但真实流程不能用”的假完成。
- 专家虽然不看代码，但会逐条操作平台；缺少详情、编辑、删除、执行反馈、异常提示、日志和数据来源时，仍会暴露为交付缺口。

### 完善目标

| 维度 | 目标 |
|---|---|
| 页面结构 | 每个模块具备总览、列表/主操作区、详情、表单、状态和日志入口 |
| 交互组件 | 补齐搜索、筛选、分页、刷新、确认、Toast、错误提示和重试 |
| 业务逻辑 | 覆盖创建、查看、编辑、删除、执行、回滚/失败处理和历史追踪 |
| 后端闭环 | 关键操作调用真实后端接口，不能只依赖前端静态数据 |
| 外部证据 | Dify、HA、Ollama、知识库或硬件侧要能看到状态变化或运行记录 |
| 测试验收 | 每个模块形成黑盒流程、接口验证和专家操作截图清单 |

### 必须纳入排期的页面

`/dashboard`、`/chat`、`/conversation-records`、`/devices`、`/sandbox`、`/monitor`、`/knowledge`、`/models`、`/agents`、`/api-console`、`/settings`、`/users`、`/docs` 都需要按 `06_功能模块完整性评审清单.md` 逐项评审。逐页缺口、优先级、依赖和证据要求统一维护在 `07_前端页面闭环整改台账.md`，避免在多份文档重复堆长表。Dify 和 HA 入口页即使采用新窗口跳转，也必须补连接测试、配置状态和打不开时的兜底说明。

### 页面整改优先级

| 批次 | 页面 | 目标 |
|---|---|---|
| 第一批 | `/dify`、`/home-assistant`、`/agents`、`/devices` | 先打通 Dify、HA、智能体实例、设备控制这条核心验收链 |
| 第二批 | `/dashboard`、`/api-console`、`/monitor`、`/chat` | 补齐专家最容易操作到的后台、接口、监控和对话闭环 |
| 第三批 | `/sandbox`、`/knowledge`、`/settings` | 处理硬件阻塞说明、RAG 证据、配置安全闭环 |
| 第四批 | `/models`、`/users`、`/docs`、`/help-docs`、`/conversation-records` | 补强管理类能力、文档说明和验收截图 |

### 交付注意

- “新增”不是完整功能；还要有详情、编辑、删除/禁用、校验、确认、日志和异常处理。
- “列表展示”不是完整功能；还要有搜索、筛选、分页、空态、错误态、数据来源和刷新机制。
- “统计卡片”不是完整功能；还要有明细、下钻、时间范围、异常定位和证据导出。
- “AI 回复成功”不是完整功能；还要有 Dify 运行 ID、后端日志、外部系统状态变化和失败处理。

## 十、当前不做的事项

- 不直接把平台改成小米云直连。
- 不把当前虚拟沙盘包装为最终真实电子沙盘。
